# CLAUDE.md — Root Governance

This file is machine-facing. It governs how any AI agent (Claude, Cursor, Copilot, etc.) works in this repo. It is not user documentation. Sub-folders have their own CLAUDE.md with scoped rules — those override this file within their scope, but never relax the rules in this root file.

**Last verified against current framework/platform documentation: July 15, 2026.** Any AI agent picking up this repo after a significant time gap should re-verify the "Current Standards" section below against live docs before assuming it's still accurate — these ecosystems move fast and this file will go stale.

## What This Project Is
A mobile-first appointment scheduler for a tattoo/PMU/brow studio. Stack: Next.js (App Router) on Vercel, Supabase (Postgres + Auth + Storage) as backend. See `/PROJECT_SPEC.md` for the full functional spec and `/docs/typescript-ai-governance.md` for TypeScript-specific failure patterns to avoid.

## Stop and Ask — When Not to Guess
If you are uncertain whether something is true — a library's current API, whether a regulation applies, whether a security control is sufficient — **stop and ask rather than proceeding on a best guess.** This applies with extra force to:
- Legal/regulatory classification questions (e.g. "does HIPAA apply to this business") — these are legal questions, not engineering ones. Build the technical controls defensively either way, but do not assert a legal conclusion in code comments, docs, or to the person you're working with.
- Anything touching booking-safety (see rule 1-2 below), security (rule 3-4), or data correctness (rule 5) where a wrong guess could ship a real vulnerability or data-integrity bug.
- Framework/platform API details you're not certain are current — this codebase has already been burned once by shipping outdated Supabase/Next.js patterns (see "Current Standards" below). If you're not sure an API is current, say so and check, rather than pattern-matching to training data.

For everything else — implementation details, naming, minor structure — state your assumption and proceed. Don't block on things that don't carry that risk.

## Current Standards (verify before relying on these — see note above)
- **Supabase API keys**: use the `publishable`/`secret` key naming (`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` / `SUPABASE_SECRET_KEY`), not the legacy `anon`/`service_role` names. Legacy keys still work during Supabase's migration window but are being phased out through the end of 2026. All client factories in `lib/supabase/` fall back to the legacy names if the new ones aren't set — don't remove that fallback, but don't write new code that only supports the legacy names either.
- **Next.js routing/session refresh**: Next.js 16 renamed `middleware.ts` to `proxy.ts` (exported function `proxy`, not `middleware`). This repo's `proxy.ts` at the root replaces what used to be `middleware.ts`. It is a network boundary only — never treat it as the authorization system. Every admin page/route still independently calls `requireStaff()`/`requireStaffApi()`.
- **Supabase identity verification**: use `supabase.auth.getClaims()` to verify a session server-side (local JWT verification, no network round-trip) rather than `getUser()`. Reserve `getUser()` for the rare case you need a guaranteed-fresh record from the Auth server itself. Never use `getSession()`'s embedded user object for an authorization decision.

## Non-Negotiable Rules
1. **The database is the source of truth for booking safety, not application code.** Double-booking prevention lives in the `appointments` exclusion constraint (see `supabase/migrations/0001_init.sql`). Never write app-layer "check availability, then insert" logic as the *only* guard — it is a UX nicety, the DB constraint is the real gate.
2. **All booking writes go through `create_booking()`** (see `supabase/migrations/0002_booking_function.sql`), not sequential inserts from route handlers. If you need to change what a booking creates, edit the SQL function and keep it atomic.
3. **RLS is the access control boundary.** Every new table needs an explicit RLS policy in the same migration that creates it. No table ships "temporarily open."
4. **Secret key is server-only.** It must never appear in a Client Component, a file under `app/**/page.tsx` marked `"use client"`, or anything bundled to the browser. It lives in `lib/supabase/admin.ts` only, which must never be imported from client code.
5. **All timestamps are UTC (`timestamptz`).** Convert to studio-local time only at render time. Never store or compare naive local time.
6. **Every admin mutation writes an audit_log row** via `lib/audit/log.ts` — not raw Supabase mutations from admin route handlers. See "Compliance" below for what that logger guarantees.
7. **Server-side re-validation is mandatory.** Anything validated in the browser (form fields, risk flags, advance-booking windows) must be re-validated server-side. Client-side validation is UX only.
8. **No raw `console.*` calls anywhere except `lib/logger/logger.ts`.** Use `logger.info/warn/error/debug` from `lib/logger/logger.ts` for operational logging. This is enforced by ESLint's `no-console` rule (see `eslint.config.mjs`) — a lint failure here is a real failure, not a style nit. See "Compliance" below for why.
9. **Every route/segment that can fail needs an error boundary**, not just a try/catch that returns JSON. Public routes: `app/(public)/error.tsx`. Admin: `app/admin/error.tsx`. Root: `app/global-error.tsx`. If you add a new top-level route group, add its own `error.tsx` rather than relying on a parent's.
10. **Follow `/docs/typescript-ai-governance.md`** for all TypeScript-level patterns (async handling, type safety, error handling). Self-check generated code against it before finalizing.
11. **`npx tsc --noEmit` and `npm run lint` must both exit 0 before any change is considered done.** Neither is optional or a "nice to have" — a type error or a lint failure (including the `no-console` rule in rule 8) is a real failure, not a style nit, and "it looks right" is not a substitute for actually running both. This project has already shipped code from an environment that couldn't run either (see README's revision notes) — that is exactly the failure mode this rule exists to catch going forward. If dependencies were changed, reinstall first; if a generated/hand-written type (e.g. `types/database.types.ts`) doesn't match what a query actually needs, fix the type, don't suppress the error.

## Compliance (SOC 2-aligned controls, HIPAA-grade floor, financial data protection)
This app collects health-screening intake answers and (eventually) payment data. **This is not a HIPAA-covered entity** — a tattoo/PMU studio is not a healthcare provider, health plan, or clearinghouse, so HIPAA does not apply as a matter of law. That said, the technical controls below are built to a HIPAA-grade *floor* anyway: encryption in transit, redaction in logs, append-only audit trail, least-exposure data access. This is a deliberate ceiling-not-floor choice to close leak/access holes before they exist, not a compliance claim — don't describe this app as "HIPAA compliant" anywhere (docs, marketing, code comments); describe the controls themselves instead.

- **Two separate logging systems, never conflated:**
  - `lib/logger/logger.ts` — operational/debug logging. Structured JSON, automatic redaction of PII/PHI-adjacent fields (see its `SENSITIVE_KEYS` list), short-retention, fine to be verbose.
  - `lib/audit/log.ts` — the compliance record. Append-only (DB-enforced — see `supabase/migrations/0003_audit_compliance.sql`, which blocks UPDATE/DELETE on `audit_log` even for admins), captures actor/role/action/category/severity/IP/user-agent, redacts snapshot fields before insert. This is what an auditor reviews. Never write PHI-adjacent free text (form answers, medical history, full names/emails/phone in bulk) into a `before`/`after` snapshot — reference IDs and status/enum fields instead.
- **Financial data**: no raw payment card data is ever stored or logged by this app — Stripe (Phase 3) handles PAN data entirely off our servers, which is itself the PCI-DSS-relevant control (this app never becomes "in scope" for cardholder data). Payment provider references (e.g. Stripe payment_intent IDs) are masked to their last 4 characters before appearing in any log or audit entry — see `maskFinancialReference()` in `lib/audit/log.ts`.
- **Access logging**: any admin read of client PII/medical intake data that goes beyond routine list views (e.g. an admin opening a specific client's full intake history) should be logged with `category: "data_access"` — this closes the same "who looked at what" gap a HIPAA access-accounting rule would require, applied here as good practice rather than a legal obligation. Not fully wired up yet — see README "Unfinished Placeholders."
- **Rate limiting** on public mutation and auth endpoints is a SOC 2 access-control expectation, not just abuse prevention — see `lib/rate-limit.ts` and its documented in-memory limitation (upgrade to Redis/Upstash before real launch).

## Intake, Consent, and Photo Capture (added post-launch — read before touching booking flow)
- **Age is a hard gate, not a soft flag.** 18+ is enforced twice independently: the `clients_must_be_18_or_older` CHECK constraint (0004 migration) and `create_booking()`'s explicit check (SQLSTATE `P1004`). This studio does not serve minors, with or without guardian consent — do not add a guardian-consent path without an explicit, separate instruction to do so; it's a different product with different legal requirements.
- **Four consent categories, one mandatory rule each:** `studio_policy`, `medical_consent`, and `photo_release` are always `required = true`; `marketing_consent` is the only category ever allowed to be `required = false`. This is enforced by CHECK constraints (`marketing_consent_must_be_optional`, `non_marketing_consent_must_be_required`) — don't work around them by inserting a new category. Never let a required consent be pre-checked or bundled with an optional one in the UI; each is its own checkbox with its own policy text.
- **Medical history is presented WITH the consent step**, per studio direction — not as a separate pre-screening screen. The data model still keeps `medical_prescreening` as its own `forms.category` (distinct from `ink_history`) — the "combined" part is a UI/flow decision in `BookingFlow.tsx`, not a schema one. Don't re-split it in the UI without checking this is still wanted.
- **Previous-ink history is its own questionnaire**, separate from medical pre-screening, and never triggers a risk flag on its own (`create_booking()` always inserts it with `flagged_high_risk = false`) — it's history, not a safety screen.
- **Face photo capture is in-app live camera only — no gallery/file upload, ever.** The entire enforcement mechanism is the absence of `<input type="file">` in `components/booking/FaceCapture.tsx` — do not add one "as a fallback," it silently defeats the entire control. No filter or image processing is applied to the captured frame (see that file's header comment). `captured_at` is set by the server clock at upload time, never by client input.
- **Photo consent must be obtained before the photo is captured**, not after — this is why the consent step precedes the photo step in `BookingFlow.tsx`. Don't reorder these without thinking through the consent sequencing implications.
- **Marketing/portfolio use is a genuinely separate consent from the mandatory photo release.** `client_photos.marketing_consent_agreement_id` is nullable and only populated when the client explicitly opted in — never infer marketing consent from the presence of a photo.
- **`client_photos` has no public RLS policy at all** — every read goes through a server-generated signed URL (`getSignedPhotoUrl()` in `lib/booking-engine/photo.ts`), every write goes through the secret-key admin client. This is intentionally the most locked-down table in the schema.
